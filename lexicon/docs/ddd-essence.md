Eric Evans' Domain-Driven Design (2003) is built around a few interlocking ideas:

- Ubiquitous Language. Developers and domain experts share one vocabulary — the same terms used in conversations, code, class names, and database tables. If the business says "shipment," the code says Shipment, not DeliveryRecord. Translation layers between "business speak" and "tech speak" are where bugs and misunderstandings breed.
- Model-driven design. The domain model isn't a diagram you draw once and forget — it is the software's structure. The model and the code evolve together. Refactoring the code refines the model; refining the model reshapes the code.
- Building blocks for expressing the model in code: Entities (things with identity that persists over time, like a Customer), Value Objects (things defined only by their attributes, like Money or an Address — interchangeable if equal), Aggregates (clusters of objects treated as one consistency boundary, accessed through a single root), Repositories (collection-like access to aggregates, hiding persistence), Domain Services (operations that don't naturally belong to any one entity), and Domain Events (things that happened in the domain).
- Bounded Contexts. A single unified model across a large system is a fantasy — terms mean different things in different parts of the business. "Customer" in Sales is not "Customer" in Support. So you draw explicit boundaries, let each context have its own model, and define how they translate at the seams (Context Map, Anti-Corruption Layer, Shared Kernel, etc.).
- Strategic design. Not all parts of a system deserve the same care. Identify the Core Domain — the part that gives the business its competitive edge — and put your best modeling effort there. Generic stuff (auth, billing) can be off-the-shelf or simpler.

The throughline: complex software fails when the model doesn't match how the business actually thinks. DDD is a set of practices for keeping those two aligned as both evolve.

## Crossing the boundaries

The seams are where Bounded Contexts meet — and Evans is pretty clear that this is where most large systems quietly rot. Two contexts each have a coherent model internally, but when they need to exchange data, you have to decide how they relate. The Context Map is the artifact that makes those relationships explicit instead of accidental.
Evans names several patterns for the relationship itself:
Shared Kernel — two teams agree to share a small subset of the model (some entities, value objects). Changes require consultation. Cheap to build, expensive to maintain because every change is a negotiation. Use only when teams are tightly aligned.
Customer/Supplier — one context is downstream and depends on another. The downstream team is the "customer" and gets a real seat at the upstream team's planning. Their needs become acceptance tests for the upstream. Works when both teams are in the same org and willing to cooperate.
Conformist — same as Customer/Supplier, but the upstream team won't or can't accommodate you. You have no leverage. So you stop fighting and just adopt their model wholesale in your context. Ugly, but honest. Common when integrating with a vendor product or a powerful internal team.
Anti-Corruption Layer (ACL) — you refuse to let the other context's model leak into yours. You build a translation layer at the boundary that converts their concepts into yours (and vice versa). Inside the ACL there are usually Adapters, Facades, and Translators. Expensive, but it protects your core domain from a messy or hostile external model. This is the pattern people reach for when integrating with legacy systems.
Open Host Service — you're the upstream and many downstream teams consume you. Instead of negotiating with each one, you publish a well-defined protocol (often paired with a Published Language — a documented, stable schema like a public API or event format). Scales better than Shared Kernel.
Separate Ways — the integration cost isn't worth it. The two contexts simply don't talk. People copy-paste between systems. Sometimes this is the right answer.
Big Ball of Mud — Evans' name for contexts where no model exists. The advice isn't "fix it" — it's "draw a boundary around it on your map, label it honestly, and put an ACL between it and anything you care about."
The practical move is: when you're integrating, name the relationship out loud. "We're Conformist to the Billing team's API" is a very different posture from "We're building an ACL against Billing." The choice determines team dynamics, not just code.
