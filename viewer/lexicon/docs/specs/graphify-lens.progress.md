## Layout overlap + test-noise fix (user feedback 2026-07-15)
User hit a live layout failure: a neighborhood rendered as dozens of fully-overlapping node boxes. Root cause: ELK `stress` treats nodes as points and does no overlap removal, so our wide mono-label rects piled up (the earlier benchmark measured aspect ratio, which missed overlap). Three-part fix, all verified live on dana-os (0 console errors):
- **Overlap-aware layout (winner: stress → sporeOverlap two-pass).** Benchmarked candidates by pairwise rect-intersection count on 3 real seeds incl. the pathological invoke_agent hop-1 (112-node contains-star): `stress` alone 459/330/210 overlaps; `radial` 3916/5253 overlaps and a stack-overflow crash on the third seed; **`stress`+`sporeOverlap` = 0/0/0 overlaps** (aspect 1.5–2.0). Implemented as a dedicated `layoutGraphify()` in `layout.ts` (bypasses layoutModel's cluster/LCA machinery — graphify is a flat ego-graph): pass 1 `stress` for shape, pass 2 `sporeOverlap` reads those positions and spreads to remove overlaps; edges are straight rect-clipped lines drawn post-layout. `GraphifyLens` calls it instead of `layoutModel`. Verified end-to-end: 0 overlaps at 112 nodes.
- **Shrunk node footprint.** `nodeSize` now ~half area (single-line label, height 30, width cap 190). Source-file subtitle moved out of the always-rendered body → shown only under the seed/selected node, plus a hover `<title>` (label — file) on every node. Kept the distinct family look (dashed rounded rect, mono, seed accent).
- **"Hide tests" toggle (default ON).** Server `neighborhood(hideTests)` filters nodes whose `sourceFile` matches test globs (`**/tests/**`, `**/test_*.py`, `**/*_test.*`, `**/*.test.*` — py+ts) **before** the node cap, so tests don't consume budget and the truncation notice stays honest; returns a `hiddenTests` count. Client toolbar toggle "hiding tests · N / showing tests". Measured on dana-os: invoke_agent 112→31 nodes (81 hidden), ThinkDecision 107→53, WorkflowGraph 83→72. The invoke_agent default view is now clean and orienting; toggling tests on shows the full 112-node starburst still spread (not stacked) thanks to sporeOverlap.
- Tests: `isTestFile` unit test + a `hidetests/` fixture (tests ordered first in adjacency to prove filter-before-cap) with a neighborhood test (excluded when on, present when off, cap applied after filtering, hiddenTests count). `bun test` 71 pass, typecheck clean.

## Mid-build decisions
- **No zod.** The codebase (loader.ts) hand-rolls validation; no zod dependency exists. The graphify parser follows that idiom — hand-rolled fail-fast checks, not a new dependency. (Plan said "minimal zod"; matching existing code style takes precedence per the build constraints.)
- **Graphify lens is a self-contained surface**, not threaded through the cold-layer `GraphFilterBar` / `kinds` / `GraphCanvas` / model-health / manual-layout machinery (all cold-layer-specific). It reuses the ELK engine (`layoutModel`) via a graphify `GraphModel` builder and its own slim SVG renderer + header. `GraphPage` early-returns `<GraphifyLens>` when `lens === "graphify"`. This matches the spec's "own surface, never mistakable for cold-layer atoms."
- **Collision signal = dangling edge endpoints.** graphify already de-dups colliding IDs before writing, so the artifact's node IDs are unique; the "12 dropped nodes" show up as edges whose source/target references a node absent from the node set. The loader counts distinct such ids and surfaces a warning; it cannot recover them.

## Gotchas
- `graphify extract <dir>` writes `graphify-out/` relative to the **scanned dir**, not cwd — it will pollute a repo working tree if pointed at one. Generate fixtures/dev artifacts only against a scratchpad copy of the source. (Already tripped and cleaned once.)
- Staleness needs git (`built_at_commit` + `git rev-list --count`); must degrade gracefully when the target isn't a git repo — git failure → staleness undefined, never fatal. Only the JSON parse is fail-fast.
- **graphify stamps `built_at_commit` from the CLI's *cwd* git repo, not the scanned project** (confirmed on dana-os: the artifact carried the lexicon repo's HEAD because extract ran from the lexicon cwd). So `commitsBehind` (which needs that commit to exist in the target repo) will be null unless the user runs `graphify extract` from *inside* the target repo. The mtime-vs-HEAD-commit-time fallback covers this — it correctly flagged dana-os stale after a later commit. Working as designed; worth surfacing to users so they run extract from the project root for an exact commits-behind count.
