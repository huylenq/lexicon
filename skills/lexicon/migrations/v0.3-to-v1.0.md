# Migration delta: v0.3 → v1.0 — YAML to XML representation flip

v1.0 flips the cold-layer wire format from YAML to XML and structuralizes every cross-reference. The DDD substrate v0.3 introduced (entity kinds, term categories, seam kinds, aggregates, shared kernels, subdomains, rationale fields) **carries through unchanged**. What changes is the *representation*: element names are the ontological types, attributes carry identity and small enums, prose elements hold the human voice, and references are uniform `<ref to="fqid"/>` elements everywhere — inline in prose (mixed content) or inside structural wrappers like `<members>`, `<participating-contexts>`. The `[[fqid]]` prose-link syntax is gone.

This delta:

- **Translates** every `lexicon/system.yaml`, `lexicon/contexts/*.yaml`, and `lexicon/surfaces/*.yaml` into the v1.0 XML shape, file-by-file.
- **Converts** `[[fqid]]` prose-links into structural `<ref to="..."/>` elements (mixed content inside prose-bearing elements).
- **Folds** v0.3 camelCase field names (`disambiguatesFrom`, `validationMode`, `lineStart`, `constrainsCode`, `participatingContexts`, `codeModules`, `relatedAtoms`, `identityRule`, `emittedWhen`, `operatesOn`, `lineEnd`, `crossCuttingTerms` if any v0.2 remnants survive) into kebab-case XML element/attribute names per the v1.0 spec.
- **Promotes** discriminated-union variants whose discriminator was a `kind:` string field to distinct element names where v1.0 specifies that (e.g. `implementation.kind: component|inline` becomes `<component-impl>` vs `<inline-impl>`).
- **Bumps** schema declaration from `schemaVersion: "0.3"` YAML field to `schema="1.0"` attribute on the root element of every file.

The conversion is **mechanical in shape but semi-mechanical in prose**. File-level YAML→XML translation is deterministic (element-tag mapping is fixed, attribute/element splits are spec-driven). Inline `[[fqid]]` → `<ref to="..."/>` conversion is mechanical for fully-qualified fqids and bare slugs that resolve unambiguously; ambiguous bare slugs surface for user choice.

For the full design rationale, see the repo-root `CLAUDE.md` and `skills/lexicon/reference/schema.md`.

## Pre-flight checks (delta-specific)

1. Confirm every `lexicon/*.yaml` file is parseable as YAML and currently declares `schemaVersion: "0.3"`. If any file declares `"0.1"` or `"0.2"`, **stop** and tell the user to run the prior deltas first — this delta assumes a v0.3-clean starting point.
2. Confirm every term has its `category:` field set (v1.0's `<term category="...">` attribute is required, no default). If any uncategorized terms exist, surface them and run the v0.2→v0.3 delta's Phase 4 (term categorization) first.
3. Confirm a git commit has been recommended. Every file in the project's `lexicon/` directory will be rewritten; a snapshot before starting is essential.
4. Confirm no v1.0 XML files coexist with v0.3 YAML in the same `lexicon/` directory. If both kinds exist, **stop** — the user picks canonical state before proceeding.
5. If `lexicon/system.md` or earlier-era markdown files exist alongside v0.3 YAML, route to the v0.x→v0.1 delta first.

## Detection phase — scan and surface

Read every YAML file under `lexicon/` (skipping `_pre-migrate-archive/`). For each, build a findings list. **Do not edit yet.**

### 1. File inventory

List every YAML file to convert:

- `lexicon/system.yaml` — the system root.
- Every `lexicon/contexts/*.yaml` — bounded-context files.
- Every `lexicon/surfaces/*.yaml` — surface files.

Report each file with: line count, `schemaVersion`, kind (`system | bounded-context | surface`), and atom counts (terms, invariants, seams, aggregates, modules, regions). The user sees the scope at a glance.

### 2. Inline `[[fqid]]` link inventory

Walk every prose-bearing YAML field across every file. The prose-bearing fields are listed in `${CLAUDE_SKILL_DIR}/reference/schema.md` under "Prose-bearing fields" — `definition`, `statement`, `rationale`, `body`, `purpose`, `narrative`, `role`, `description`, `identityRule`, `equality`, `returns`, `emittedWhen`, `payload`, plus `reason` on deliberate omissions and `description` on overlays. Use the same regex the v0.3 loader uses (`\[\[([A-Za-z0-9][A-Za-z0-9\/\-_.]*?)(?:\|[^\]]+)?\]\]`), skipping `[[…]]` patterns inside backtick code spans.

For each `[[fqid]]` occurrence, classify:

- **Fully-qualified** (`kernel/identity/user-id`, `context/inference`, `inference/scan-queue/invariant/...`) — these convert mechanically to `<ref to="<fqid>"/>` with no judgment needed.
- **Bare slug, unambiguous** (`scan-queue` inside `context/inference` resolves to exactly one entity via the owner-scoped fallback chain) — these convert mechanically too. Use the resolver logic identical to the v0.3 loader's `resolveFqid`.
- **Bare slug, ambiguous** (the slug resolves to >1 candidate, or to 0 candidates) — surface for user disambiguation. Don't auto-pick.
- **Backtick-wrapped code identifier** (e.g. ``the `foo` function``) — leave alone. The v0.3 loader's code-span skipping rule still applies; these are code references, not lexicon refs.

Report total occurrence counts in each bucket. The bare-slug-ambiguous count is the load-bearing number for cadence planning — if it exceeds 10, expect a multi-turn distillation; if it's under 3, the user clears the conversion in a single message.

### 3. Discriminated-union promotions

The v0.3 surface schema uses `implementation: {kind: "component" | "inline"}` discriminated unions on regions. v1.0 promotes the discriminator to the element name (`<component-impl>` vs `<inline-impl>`). List every `surfaces/*.yaml` and the count of region implementations of each variant. Mechanical; no judgment needed.

### 4. Field renames (camelCase → kebab-case)

The mapping table for v0.3 YAML field names to v1.0 XML element/attribute names:

| v0.3 YAML field | v1.0 XML location |
|---|---|
| `disambiguatesFrom` (term) | `<disambiguates-from>` element with `<ref/>` children |
| `validationMode` (invariant) | `mode=` attribute on `<invariant>` |
| `constrainsCode` (invariant) | `<constrains-code>` element with `<code-anchor/>` children |
| `boundaryRules` (context) | Repeated `<boundary-rule>` sibling elements |
| `participatingContexts` (kernel) | `<participating-contexts>` element with `<ref/>` children |
| `codeModules` (context) | `<code-modules>` element with `<path>` children |
| `lineStart` / `lineEnd` (anchor) | `line-start=` / `line-end=` attributes |
| `relatedAtoms` (omission) | `<related-atoms>` element with `<ref/>` children |
| `identityRule` (term) | `<identity-rule>` element |
| `emittedWhen` (term) | `<emitted-when>` element |
| `operatesOn` (term) | `<operates-on>` element with `<ref/>` children |
| `deliberateOmissions` (system) | Repeated `<deliberate-omission>` sibling elements |
| `sharedKernels` (system) | Repeated `<shared-kernel>` sibling elements |
| `overlays` (system) | Repeated `<overlay>` sibling elements |
| `triggers` (omission) | Repeated `<trigger>` sibling elements |
| `items` (overlay) | `<items>` element with `<item>` children |
| `schemaVersion: "..."` field | `schema="..."` attribute on root element |
| `kind: <name>` field | Root element name carries the kind; field removed |
| `id: <slug>` field | `id=` attribute on root element |
| `name: <text>` field | `<name>` child element |

The mapping is exhaustive for v1.0; if a v0.3 file contains a top-level key not in this list, either v0.2-conform-residue remains (route to earlier delta first) or the spec gained a new field without updating this delta (a v1.0 spec/migration mismatch — surface to the user).

### 5. Anchor expansion candidates

Walk every YAML `symbols:` and `constrainsCode:` list. Each entry has the shape `{file, lineStart?, lineEnd?, symbol?}`. In v1.0 these become `<code-anchor file="..." line-start="..." line-end="..." symbol="..."/>` self-closing elements. Mechanical — no judgment. Report counts only.

## Apply phase 1 — File conversion (mechanical)

For each YAML file inventoried in detection step 1:

1. **Parse the file** as YAML using the same loader logic v0.3 used (the structural shape is already validated by pre-flight check 1).
2. **Build the equivalent v1.0 XML structure** by:
   - Setting the root element name from the file kind (`<system>`, `<bounded-context>`, `<surface>`).
   - Emitting `schema="1.0"` as the first attribute on the root, then `id=`, then any other root attributes (`subdomain=`, `route=`).
   - Walking each top-level YAML key in the order listed in `${CLAUDE_SKILL_DIR}/reference/schema.md`'s entity-shape examples. For each key, apply the rename map from detection step 4.
   - For `name:` fields, emit as `<name>` child elements.
   - For prose-bearing fields (`purpose`, `narrative`, `body`, `definition`, etc.), emit as multi-line prose elements with content indented per the canonical serialization conventions.
   - For array fields whose elements are atoms (`terms:`, `invariants:`, `seams:`, …), emit each as a sibling element of the appropriate v1.0 element name. No wrapping `<terms>` etc. — atoms sit directly inside their parent.
   - For array fields whose elements are refs (`contexts:`, `members:`, `participatingContexts:`, etc.), emit the wrapper element from the rename map containing one `<ref to="<fqid>"/>` per array entry.
   - For string-array fields without ref semantics (`codeModules`, `triggers`, `items`), emit the wrapper element containing one type-specific child per array entry (`<path>`, `<trigger>`, `<item>`).
   - For code anchors, emit `<code-anchor>` self-closing elements with attributes.
   - For region implementations, dispatch on the YAML `kind:` field to emit `<component-impl>` or `<inline-impl>`.
3. **Apply canonical serialization conventions** (`${CLAUDE_SKILL_DIR}/reference/schema.md` "Canonical serialization conventions"):
   - 2-space indent.
   - Attribute order: `id` first; structural attributes (`schema`, `category`, `kind`, `mode`, `status`, `subdomain`, `route`) next; semantic attributes (`file`, `line-start`, `line-end`, `symbol`, `import`, `to`, `ref`) last.
   - Short elements on one line; prose elements always multi-line.
   - XML entity escapes (`&lt;`, `&gt;`, `&amp;`) inside prose where literal angle brackets appear.
   - Single trailing newline at EOF; no trailing whitespace.
4. **Write the new file** at the same path with `.xml` extension (`system.yaml` → `system.xml`, `contexts/inference.yaml` → `contexts/inference.xml`, etc.). Do not delete the YAML originals in this phase — Phase 4 archives them.

Run the conversion in a single batch across all files. No per-file user gate; this is structural and deterministic. If any file fails to convert (a key the rename map doesn't cover, a malformed YAML structure), **stop the batch and surface the specific file and field** so the user can decide whether to fix the source or extend this delta. Don't proceed with a partial conversion.

## Apply phase 2 — Prose ref conversion (mostly mechanical, escalation on ambiguity)

For each prose-bearing element in the newly-written XML files, walk its text content and replace every `[[fqid]]` occurrence per the buckets from detection step 2:

1. **Fully-qualified `[[fqid]]`** — replace with `<ref to="<fqid>"/>` directly inline (mixed content). Single batch, no prompts.
2. **Bare slug, unambiguous** — replace with `<ref to="<bare-slug>"/>` (preserving the bare form so the resolver's owner-scoped fallback continues to apply at load time). Single batch, no prompts.
3. **Bare slug, ambiguous** — surface to the user one at a time:
   > In `<file>` § `<element-path>`, the prose contains `[[<slug>]]` which could resolve to:
   > - `<fqid-candidate-1>`
   > - `<fqid-candidate-2>`
   >
   > Pick which one, or say "leave as-is" to skip (the prose stays unchanged; you can clean up later via `crystallize`).
   
   Apply the user's pick; move to the next ambiguous occurrence.
4. **Backtick-wrapped names** — leave alone. The v0.1→v0.2 rule ("don't auto-rewrite code-identifier-shaped names; err on the side of leaving them") preserves into v1.0.

If the ambiguous-bare-slug count from detection exceeded 10, propose **batched disambiguation** mid-phase: *"there are <N> bare-slug refs left to disambiguate; would you like to handle the remaining ones one-by-one, or skip them (leave as-is in prose) and revisit via `crystallize` later?"* Either path is valid — the unconverted `[[…]]` markers stay in the prose and the loader will warn about them at load time, which is itself a useful triage signal.

## Apply phase 3 — Schema bump

For each newly-written XML file, confirm the root element carries `schema="1.0"` as its first or second attribute. The conversion in Phase 1 should have emitted this already; this phase is a safety check, not an edit. If any file is missing the attribute, add it now.

## Apply phase 4 — Archive YAML originals

Move every original `.yaml` file to `lexicon/_pre-migrate-archive/v0.3-to-v1.0/` preserving the directory structure:

- `lexicon/system.yaml` → `lexicon/_pre-migrate-archive/v0.3-to-v1.0/system.yaml`
- `lexicon/contexts/inference.yaml` → `lexicon/_pre-migrate-archive/v0.3-to-v1.0/contexts/inference.yaml`
- `lexicon/surfaces/reading-room.yaml` → `lexicon/_pre-migrate-archive/v0.3-to-v1.0/surfaces/reading-room.yaml`

Use `git mv` (the user can recover them via git history, but a working-tree archive makes inspection cheap during the post-migration review). The viewer's loader already skips `_pre-migrate-archive/` so these archived files are inert.

## Validate phase

Two-list validation: structural (errors) and discipline (warnings).

### Structural (errors — block until resolved)

- Every `lexicon/*.xml` file parses as well-formed XML.
- Every file's root element is one of `<system>`, `<bounded-context>`, `<surface>`.
- Every root element carries `schema="1.0"`.
- Every atom element carries a valid `id=` slug attribute (regex `[a-z0-9][a-z0-9-]*`).
- Every term carries a `category=` attribute set to one of `entity | value | service | event | concept`.
- Every seam carries a `kind=` attribute set to one of the nine context-map enum values.
- Every structural `<ref to="..."/>` resolves against the project's entity map (the v1.0 loader's fallback chain). Unresolved structural refs become **errors** at validation time (different from v0.3 where they were warnings — v1.0 file-conversion shouldn't introduce dangling refs).
- Every region carries exactly one of `<component-impl>` or `<inline-impl>`.
- No `.yaml` files remain in `lexicon/` outside `_pre-migrate-archive/`.

### Discipline (warnings — surface, don't block)

- Bare-slug ambiguous `[[…]]` occurrences left unconverted in prose. Report count and list the first 10 with their file + element path.
- Prose-embedded refs that resolved at conversion time but show as warnings under the v1.0 loader (this would indicate a resolver behavior change, not a conversion bug — surface for investigation).
- Empty `<rationale>` elements that previously held `[[…]]`-only content (suggests the original rationale was a single ref-pointer with no surrounding argument — flag for `crystallize`).
- Element name typos in v0.3 YAML that the conversion preserved verbatim because the rename map didn't recognize them (these become invalid XML element names if they survive; the structural check above already errors on these — this discipline warning is redundant unless validation is run in a permissive mode).
- Any file where the XML output line count is >2× the YAML input line count, suggesting the conversion introduced verbose nesting where flatter would have worked (manual review recommended).

## What this delta deliberately does NOT do

- **Doesn't rewrite content semantics.** Field renames and structural translations preserve every term, invariant, seam, etc. verbatim. If a v0.3 term had a stale definition, the v1.0 XML carries the same stale definition — the user fixes content via `crystallize`, not via this delta.
- **Doesn't auto-categorize remaining uncategorized terms.** Pre-flight check 2 routes this back to the v0.2→v0.3 delta. v1.0 conversion assumes every term is already categorized.
- **Doesn't classify `kind: unknown` seams.** Same principle — v0.3 distillation is the place to triage seams.
- **Doesn't bundle the term-category-as-element-type refinement.** Promoting `<term category="value">` to `<value>` element is a future ontological refinement (v1.1+); v1.0 keeps sub-discriminations as attributes.
- **Doesn't introduce XML namespaces.** Single namespace for v1.0; project-specific extensions (`<dentalml:cbct-scan>`) are a future-version concern.
- **Doesn't validate against the XSD at load time.** The XSD ships as a documentation/editor-tooling artifact; the v1.0 loader's TypeScript traversal is authoritative for runtime validation. CI cross-check via `xmllint` is a v1.1 nice-to-have.

## On the "real `<ref>` everywhere" choice

The most load-bearing decision in v1.0 is that all cross-references are structural `<ref to="fqid"/>` elements rather than `[[fqid]]` syntax embedded in prose strings. Phase 2 is where this decision shows up in the migration cost.

The conservative ambiguity rules above (auto-convert fully-qualified fqids in batch, auto-convert bare slugs that resolve unambiguously in batch, surface bare-slug-ambiguous cases one-at-a-time, leave backtick-wrapped names alone) keep this from becoming a thousand-prompt interactive ordeal even on lexicons with rich prose.

If the user's lexicon was heavy on bare-slug `[[…]]` usage and the ambiguity count is high, the right move is to skip Phase 2's per-item disambiguation entirely and run it as a follow-up via `crystallize`: the unconverted `[[…]]` markers stay in the XML prose (still valid mixed content from the parser's perspective; the v1.0 loader will emit warnings at load time for any prose that contains `[[…]]` since v1.0 has no native `[[fqid]]` semantics). Those warnings *are* the triage list — the user can address them at a time of their choosing without blocking the format flip.
