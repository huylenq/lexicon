# Migration delta: v0.2 → v0.3 DDD-faithful schema

v0.3 reshapes the cold-layer vocabulary to follow Eric Evans' Domain-Driven Design building blocks faithfully. The v0.2 schema was Evans-flavored but carried inventions that don't appear in DDD (the `decision` kind, the untyped `crossCuttingTerms` bag) and omitted primitives Evans treats as load-bearing (Entity vs. Value Object, Aggregates, Domain Events, typed context-map relationships, Subdomains, Evans-modules).

This delta:

- **Removes** the `decision` entity kind. ADR YAML files archive under `lexicon/_pre-migrate-archive/decisions/`. Per-ADR rationale-lift into affected atoms is offered but optional.
- **Replaces** `crossCuttingTerms` / `crossCuttingInvariants` with `sharedKernels` — typed shared sub-models with participating contexts and rationale.
- **Renames** `bounded-context.modules` (file globs) to `codeModules` and frees the `modules` name for Evans-sense concept clusters.
- **Adds** `term.category` (entity | value | service | event | concept), `aggregate` and `module` entity kinds, typed `seam.kind` (Evans context-map enum + `unknown`), `subdomain` on bounded-context, and `rationale` fields on more atoms.
- **Bumps** `schemaVersion` to `"0.3"` on every touched file.

This delta is **interpretive**, not mechanical — categorizing terms, grouping cross-cutting entries into kernels, and classifying seam kinds are judgment calls the user makes. The agent surfaces candidates and asks per-item; it does not auto-classify.

For the full design rationale, see `DESIGN-v0.3.md` at the repo root.

## Pre-flight checks (delta-specific)

1. Confirm every `lexicon/*.yaml` file is parseable as YAML and currently declares `schemaVersion: "0.1"` or `"0.2"`. If any file declares `"0.3"` already with no detection findings, refuse: "Already on v0.3 with no structural violations; nothing for me to do."
2. Confirm a git commit has been recommended. The delta makes interpretive interview-driven edits; a snapshot before starting is essential.
3. If `lexicon/decisions/` exists with `.yaml` files in it, note it for Phase 1. If `lexicon/decisions/` exists but is empty, plan to delete it at the end.
4. If any non-canonical top-level keys remain from a v0.1-conform that never ran the v0.1→v0.2 delta, **stop** and tell the user to run the v0.1→v0.2 delta first. This delta assumes a v0.2-clean starting point.

## Detection phase — scan and surface

Read every file in `lexicon/`. For each, build a findings list. **Do not edit yet.**

### 1. ADRs to archive

List every `lexicon/decisions/*.yaml` file. For each:

- The ADR's `id`, `title`, `date`, `status`.
- The `affects:` list (the atoms whose rationale could absorb the decision's argument).
- Whether `supersedes` / `supersededBy` chains exist (these are lost in v0.3; surface the chain so the user knows what they're forgoing).
- The lengths of the `context`, `decision`, `consequences`, `alternatives` blocks — to size the optional rationale-lift work.

### 2. Cross-cutting entries to group

List every entry under `system.crossCuttingTerms` and `system.crossCuttingInvariants`. For each entry, compute:

- The set of contexts that reference it (via `disambiguatesFrom`, prose `[[fqid]]` links in any file, or being named in a context's `purpose` / `narrative` — best-effort substring scan against the entry's slug).
- A proposed kernel grouping: cluster entries by overlapping context sets, *then* split by **codomain** (what the entries model). The context-overlap heuristic alone collapses tight-UL platforms into one mega-kernel (round-1 eir pilot: every cross-cutting entry shared the same execution context, so naive grouping produced one bag). After computing context-overlap clusters, ask "do these entries describe **one** shared model, or several?" Split per codomain when several (e.g. pipeline-shape vs run-and-event vs resource-options).
- **Anti-pattern flag**: if a proposed kernel would describe "system-wide vocabulary every context happens to use" with no specific shared model to coordinate on, mark it as a **weak kernel candidate**. Round-1 viewer pilot produced exactly this — a "viewer-vocabulary" kernel whose own description admitted it wasn't a kernel in the strong DDD sense. Weak kernels should propose **either** (a) promotion of each term to a single owning context (sibling contexts reference) **or** (b) a `published-language` seam between the contexts that agree on the format. Don't ship the weak kernel.

The output is a draft kernel list with proposed memberships AND a list of weak-kernel candidates flagged for the user's "kernel or not" call; the user refines in the apply phase.

### 3. Module renames

Every `bounded-context` file with a top-level `modules: [<string>]` (file globs) needs the field renamed to `codeModules`. List the files and the count of glob entries each.

### 4. Term category candidates

Walk every term across the project (kernel-scoped, context-scoped). For each term:

- If `symbols` is present and points at a class/struct definition → entity candidate (carries identity).
- If `symbols` is present and points at a function/method or stateless type → service or value candidate.
- If the name ends in past-tense suffix (`-ed`, `-Settled`, `-Placed`, `-Opened`) → event candidate.
- If the term has no `symbols` and the definition reads as scaffolding → concept (default).

Surface a categorization triage list. The agent's guess is a hint, not a commitment.

### 5. Seam kind classification

Every seam in every bounded-context file currently has no `kind` field. List each seam with:

- Its `name` and `description`.
- Its `participants` list (or inferred participants from the seam's context).
- Whether the description text contains keywords that hint at a specific kind:
  - "translate" / "adapt" / "wrap" → anticorruption-layer
  - "agree on" / "shared format" → published-language
  - "downstream" / "consumes" / "depends on" → conformist or customer-supplier (ambiguous)
  - "shared model" / "lockstep" → shared-kernel
  - "no integration" / "deliberately separate" → separate-ways

Surface guesses as hints; the user picks per-seam.

### 6. Aggregate / module / subdomain opportunities

These are additive — projects can ship without them. Scan opportunistically:

- **Aggregate candidates** — a term with `symbols` pointing at a class that owns child entities (heuristic: classes with composition relationships in the code, or terms whose definitions mention "lifecycle" / "consistency" / "owns").
- **Module candidates** — when a context has ≥8 atoms, look for cohesive subgroups by name prefix or shared `[[fqid]]` co-occurrence in prose.
- **Subdomain candidates** — for each bounded-context, classify by purpose:
  - Names the project's "differentiator" / "core IP" / "the main value" → core
  - Generic concern (auth, billing, scheduling, telemetry) → generic
  - Otherwise → supporting

Surface the candidates; do not propose to apply unless the user opts in.

Surface in chat:

Then ask: which findings to apply, in what order, all-or-batch. Default: walk apply phases in order, ask the user per item during each.

## Apply phase 1 — Archive ADRs (and optionally lift content)

For each ADR file in `lexicon/decisions/`:

1. **Default: archive without lift.** Move the file to `lexicon/_pre-migrate-archive/decisions/<original-filename>`. Preserves the YAML verbatim; the user can recover anything later. **This is the safe autonomous default** — if the migration runs without a user (pilot mode), or the user declines the lift, archive-only is the right outcome. Round-1 eir pilot defaulted to archive-only on all 6 ADRs and lost some defensible lifts; that's a tolerable failure mode compared to a wrong autonomous lift.
2. **Optionally: lift content into rationale fields.** For each ADR, surface a per-section proposal:

   - If `affects:` lists a single atom, propose its `decision:` block as a `rationale:` on that atom.
   - If `affects:` lists multiple atoms, propose a `rationale:` on **the atom whose definition the decision most directly justifies** — usually the seam (if the ADR justifies a context-map relationship), the aggregate (if it justifies a boundary), or the invariant (if it justifies a constraint). When the user can't pick, default to archive-only and surface in the migration report as a follow-up for `lex-crystallize`.
   - The `context:` and `alternatives:` blocks are conversation, not rationale-shaped. Surface them but default to "don't lift" — they belong in a future development-journal mechanism, not here.
   - The `consequences:` block sometimes lifts cleanly into `rationale` on an aggregate or seam (when the ADR justifies a structural choice).

   Apply per-section on user yes.

3. **`supersedes` / `supersededBy` chains.** Log the chain into `lexicon/migrate.md` so the user can grep for it later; do not attempt to encode it in v0.3.

4. **Prose-link rewrites.** After archival, walk every prose-bearing field in every file and rewrite `[[decision/ADR-N]]` references (or shorthand `[[ADR-N]]`) to `(see archived ADR-N)` — plain prose, not a structured link. The archived file isn't part of the resolved graph, so the link can't resolve; a prose "see archived" pointer is the honest replacement.

After every ADR file in `lexicon/decisions/` is archived, **delete the empty `lexicon/decisions/` directory**.

### What "don't touch" still means

If an ADR file is not YAML or fails to parse, leave it where it is and flag in the report. Don't move a file you can't read.

## Apply phase 2 — Rename `modules` → `codeModules`

For each bounded-context file with `modules: [<string>]` (string array of file globs):

- Rename the field to `codeModules`. Preserve the array verbatim.
- This is **mechanical** — no interview, no per-file confirmation needed beyond the initial all-or-batch agreement.

If a bounded-context has `modules: [<object>]` already (object array), it must be invalid v0.2 since v0.2's modules was string-only. Flag for user review.

## Apply phase 3 — Group cross-cutting into shared kernels

The most interpretive phase. Walk the user through each proposed kernel **one at a time** (the cadence rule from v0.1→v0.2 applies for any project with >3 proposed kernels).

For each proposed kernel:

1. **Show the proposal.** Name, member terms, member invariants, inferred participating contexts, agent's draft `description:` and `rationale:`.
2. **Refine via interview.** The user can:
   - Rename the kernel.
   - Add or remove members.
   - Edit participating contexts.
   - Edit the description and rationale (or ask the agent to redraft).
   - Reject the kernel (members will be handled separately — see step 4).
3. **Apply.** Emit the kernel as a `sharedKernels[]` entry on `system.yaml`. Member terms get fqid `kernel/<kid>/<tid>`; invariants get `kernel/<kid>/invariant/<iid>`. Delete the corresponding entries from `crossCuttingTerms` / `crossCuttingInvariants`.
4. **Unkernelled entries.** For each cross-cutting entry that didn't fit any kernel:
   - If it's referenced by exactly one context, propose moving it into that context's terms/invariants list.
   - If it's referenced by zero contexts (orphan), propose deletion or promotion to a singleton kernel — user picks.
5. **Rewrite prose `[[fqid]]` links.** After all kernels are emitted, walk every prose-bearing field in every file and update any `[[<old-slug>]]` whose `<old-slug>` now lives in a kernel — point at the qualified form `[[kernel/<kid>/<slug>]]`. The link-rewrite is mechanical (slug-by-slug substitution); show a diff before applying.

After all entries are handled, delete the (now empty) `crossCuttingTerms` and `crossCuttingInvariants` arrays from `system.yaml`.

## Apply phase 4 — Categorize terms

Walk every term **one per turn** (no batching). For each:

1. Show the term's `name`, `definition`, `symbols` (if any), and current owner (context or kernel).
2. Show the agent's guess (from detection phase).
3. Ask the user to pick: entity / value / service / event / concept.
4. If entity → optionally draft `identityRule:`. If value → optionally draft `equality:`. Etc.
5. Apply by adding `category:` and any category-specific fields to the term's YAML entry.

### `value` requires equality — or pick `concept` instead

If the user picks `value` for a term that has no clear equality semantics (CSS-variable names, theme flags, named keyframes, registry keys, type aliases for opaque strings), surface explicitly: **"this term has no obvious equality story — pick `concept` instead."** Round-1 pilots produced ~6 terms tagged `value` with absent or filler `equality:` ("String equality.") — the resolver accepts these but they teach the wrong lesson. Discipline: a `value` without equality is a `concept` mis-labelled. The validate phase counts these and flags them.

Defaults: if the user skips, leave `category` unset — the resolver treats absent as `concept`. The user can always re-categorize later via `lex-crystallize`.

For projects with > 20 terms, the user may want to do this in two passes: first set category for every term, then come back for category-specific fields. Honor that pacing.

### Autonomous-mode escape (pilot / agent-only runs)

The "one per turn, no batching" rule is for **user-in-the-loop** migrations. When this delta runs without a user present (agent piloting an autonomous migration before showing results to the human), batching is permitted under explicit confidence flagging:

- Group terms by the agent's confidence: **high** (symbols clearly identify entity/value/service/event semantics), **medium** (some signal but ambiguous), **low** (no code anchor, scaffolding name).
- Apply high-confidence categorizations in a single batch.
- Surface medium and low in the migration report as a triage list for human review.
- Leave low-confidence terms at default (concept).

The validate phase MUST count uncategorized terms (those defaulting to concept) and report the count even when the migration "completed" — silent default to concept is how Phase 4 gets short-circuited (round-1 pilots demonstrated this: my own mechanical viewer migration categorized 5/27 terms and passed validate).

## Apply phase 5 — Classify seam kinds

Walk every seam **one per turn**. For each:

1. Show the seam's `name`, `description`, current `participants`.
2. Show the agent's guess from the detection phase.
3. Ask the user to pick from the nine kinds (eight Evans + `unknown`) **— or `demote`**, if the seam is actually intra-context cohesion rather than a context-map relationship (see below).
4. If the chosen kind is asymmetric, ask which participant is `upstream` and which is `downstream`. If symmetric, keep `participants`.
5. Optionally draft a `rationale:` capturing why this kind was chosen.
6. Apply by adding `kind:`, `upstream`/`downstream`, and `rationale:` to the seam's YAML.

### Demote-to-non-seam branch

Sometimes what looks like a seam is actually intra-context authoring discipline ("the inline `@theme` block always declares its tokens before the regular CSS layer; the regular layer never redeclares them"). These aren't context-map relationships — they're invariants. Round-1 pilots found three of these stuck at `kind: unknown` on eir's design-system because `unknown` was the only legal escape.

For each seam, ask: *is this actually about how two **contexts** interact, or about how files/modules inside **one** context cohere?* If the latter, **demote**:
- Single-participant seams (`participants: [<one>]` for a symmetric kind, no upstream/downstream for an asymmetric) → almost always a demote candidate; the loader flags these as warnings.
- Authoring-discipline seams (about file/module conventions within a context) → demote to a `boundaryRule` (if directional) or an `invariant` with `validationMode: principle`.
- Cohesion seams (about how parts of one model fit together) → usually an `invariant`.

When the user picks demote, the migration creates the replacement (boundary rule or invariant) and deletes the seam. Log the demotion in `migrate.md`.

If the user chooses `unknown` (or skips), the resolver flags it as a warning at load time — that's by design. The user can return to it later. **But if `unknown` is the third or fourth seam in a row picked for the same context's design-system or authoring concerns, propose the demote pattern explicitly rather than letting them accumulate.**

## Apply phase 6 — Optional aggregates, modules, subdomains

Only if the user opted in during the detection-output triage. Each is a separate interview pass:

- **Aggregate creation.** For each candidate, ask: "Is `<term>` an aggregate root? If so, what are its members and which invariants are transactional to it?" Apply by adding to the context's `aggregates: []` array. Validate that the root has `category: entity` — if not, surface and let the user fix the categorization first.
- **Module creation.** For each candidate, ask: "Within `<context>`, do you want to name the subgroup `<inferred-name>` containing `[<atoms>]`?" Apply by adding to the context's `modules: []` array (the Evans-sense modules — distinct from `codeModules`).
- **Subdomain classification.** For each context, ask: "Core / supporting / generic / overlay, or skip?" Apply by adding a top-level `subdomain:` field. The `overlay` value is the lexicon extension to Evans for installation-specific contexts (medical/legal/retail/etc. tiers swapped per deployment); pair with a system-level `overlays[]` entry when applicable.

None of these are required for v0.3 to load. Empty `aggregates`, absent `modules`, absent `subdomain` are all valid.

## Apply phase 7 — Optional rationale fields elsewhere

After the structural phases, offer one final pass: for atoms that gained rationale-bearing slots in v0.3 (`seam`, `aggregate`, `module`, `boundary-rule`, terms via category-specific guidance), surface any whose rationale is still empty and ask: "Want to add why?" The user can populate or skip per atom.

This is the **lowest-priority phase**. Skip entirely on first pass; the user can come back via `lex-crystallize`.

## Apply phase 8 — Bump `schemaVersion`

For every file that received any v0.3-specific edit (renamed field, lifted to kernel, added category, classified seam, gained an aggregate/module, gained a subdomain, or simply was touched at all), update `schemaVersion:` from `"0.2"` (or `"0.1"`) to `"0.3"`.

After this phase, **every file in `lexicon/` should declare `"0.3"`**. Files that the migration deliberately didn't touch (e.g. surfaces whose v0.2 shape is unchanged in v0.3) still bump — the loader is strict and only loads `"0.3"`.

If for any reason a file can't be bumped (parse error, unresolved interpretive question), flag it; the user fixes manually.

## Validate phase

After all edits land, re-parse every file and run these checks:

### Structural (errors)

- zod-validates against the v0.3 schema (no `crossCuttingTerms`, no `kind: decision`, no string `modules`).
- Every structured ref resolves: `sharedKernels[].participatingContexts`, `aggregates[].root`, `aggregates[].members`, `aggregates[].invariants`, `modules[].members`, seam `upstream`/`downstream`/`participants`, term `operatesOn`/`consumers`.
- Every `[[fqid]]` in prose resolves (kernel-scoped slugs now form a new fqid namespace).
- Asymmetric seam kinds carry upstream + downstream; symmetric kinds carry participants (≥2).
- `schemaVersion: "0.3"` on every file.
- `lexicon/decisions/` directory does not exist.

### Discipline (warnings — surface, don't fail)

These are the silent-incompleteness checks that round-1 pilots surfaced. Run them every time; report counts even when zero.

- **Uncategorized term count.** Walk every term across the project. Count those with no `category:` field or `category: concept`. Surface as: "N of M terms left at default `concept` — if >50%, Phase 4 is incomplete." Hide nothing.
- **`value` terms without `equality:`.** Each one is a likely mis-categorization (should be `concept`). Surface the list.
- **Aggregate root category coherence.** Aggregates whose `root` resolves to a term with `category != entity`. (Already covered by structural; restate here as a discipline gate.)
- **`operatesOn` category coherence.** Service-category terms whose `operatesOn:` references include terms with `category` in `{concept, service, event}`. Per the schema, `operatesOn` should reference entity- or value-category terms. Round-1 dany pilot surfaced this; not loader-enforced.
- **Mirror seams.** Two seams with the same `id` in different context files. Round-1 eir pilot found `atomic-vs-group` and `spec-vs-runtime` declared verbatim in two contexts each. Recommend consolidating to one canonical home (usually the downstream side).
- **Single-participant symmetric seams.** Seams with a symmetric `kind` (shared-kernel / published-language / partnership / separate-ways) and `participants.length < 2`. These are malformed for the chosen kind — usually a "should have demoted" signal.
- **Seams stuck at `kind: unknown`.** Count and list. Three or more in one context suggests Phase 5 was short-circuited.
- **Rationale gaps.** Aggregates / shared-kernels / typed seams (kind != unknown) / boundary rules without `rationale:`. Surface the count and list the first 10.
- **Stale v0.2 vocabulary in prose.** Grep every prose-bearing field (`purpose`, `narrative`, `body`, `definition`, `statement`, `rationale`, `description`, `role`, category-specific prose fields) for the strings `decision`, `affects:`, `supersedes`, `crossCutting`. Each hit is content drift — the migration removed the structural concepts but the prose still describes them. Surface as rewrite candidates (round-1 viewer pilot's `lexicon-loading.yaml` had several).

Any structural failure (the first list): surface, ask the user. Do not auto-revert. Discipline warnings (the second list) ship as part of the migration report — they're triage, not blockers.
